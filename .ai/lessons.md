- 2026-11-15 — CI runners set `GITHUB_*` env vars on every job (GitHub Actions: `GITHUB_API_URL=https://api.github.com`, `GITHUB_SERVER_URL`, `GITHUB_ACTIONS`…; Codespaces and some PaaS too). Never name app config after them: our boot refusal for `GITHUB_API_URL` without `ALLOW_TEST_OVERRIDES=1` failed every unit test that read the real `process.env` in CI while passing locally. App-owned override vars carry the `DEVMENTOR_` prefix (`DEVMENTOR_GITHUB_OAUTH_URL`/`DEVMENTOR_GITHUB_API_URL`), and tests that read `process.env` first clear `ENV_KEYS` (`config/env.ts`) with `vi.stubEnv(key, undefined)`. Reproduce CI locally with `GITHUB_API_URL=https://api.github.com GITHUB_ACTIONS=true npm run test:coverage`.

A dev-only CLI guarded by `NODE_ENV=production` alone is not a guard: `NODE_ENV` defaults to development, so check what it writes to (`db:seed` refuses a non-local `DATABASE_URL` host unless `--allow-remote-database`).

A race test that starts both calls at once may never hit the window; stagger the second call by 0–9 ms over rounds.

- 2026-11-14 — v8 coverage miscounts branches after an `await` inside a conditional expression (`x === null ? null : await em.findOne(…)` followed by an `if`): the full run reported a covered `if` as uncovered (negative else count in `coverage-final.json`), a single-file run did not. - 2026-11-14 — MikroORM 7: a nullable `manyToOne` gets `on delete set null` in the generated migration unless you set `.deleteRule(...)` — check the FK rule against your CHECKs (`invitations.accepted_by_id` uses `restrict`; `set null` would only trip the accepted-pair CHECK). - 2026-11-14 — TS scripts that import `@devmentor/core`: run them with `tsx --conditions=react-server` (`server-only` throws without the condition) and `--env-file-if-exists=.env` (tsx passes Node flags through; existing env vars win), and name them `.mts` — the root package is CommonJS, so a `.ts` entry cannot use top-level await. - 2026-11-14 — MikroORM 7 `em.execute(sql, params)` does not send bind parameters: it replaces `?` client-side with platform-escaped literals (so never put a literal `?` operator in such SQL, cast with `?::timestamptz`). - 2026-10-26 — Check-then-write through the MikroORM unit of work is not atomic: `findOne` + set + `flush` becomes `UPDATE … WHERE id = ?`, so two requests both pass the check (GitHub link race). Put the condition in the write (`em.nativeUpdate(Entity, { id, field: null }, data)` → affected rows) and `em.refreshOrFail(entity)` afterwards (nativeUpdate bypasses the identity map). When the check guards writes to *other* rows (resend: "no password" → retire tokens + insert one), a conditional write cannot carry it: serialize on the parent row in one transaction — `em.findOne(User, id, { lockMode: LockMode.PESSIMISTIC_WRITE, refresh: true })` (`refresh`, or the identity map answers with the pre-lock copy) — and take the same lock in every writer of that state (set-password). Build such options at call time: a module-level `LockMode.X` (or a module-level zod schema using `STACK_TAGS`) breaks tests that mock `@devmentor/db` partially (`container.test.ts` does) — wrap it in a function. Also: `ReadableStream.cancel()` on an errored body rejects — never let cleanup replace the real error (`packages/core/src/http/outbound.ts`).
