### Phase 1 manual test
- [Bug] `mock-unverified` under `next dev` landed on `/sign-in?error=unexpected` (log: `GithubEmailUnverifiedError` … "Unhandled redirect error") instead of `github_email_unverified` — **fixed**. Root cause: the DI container is one per process (`globalThis`) and is built by whichever server bundle calls it first (here a page, `ssr/` chunk), so every service — and the `AppError` subclasses it throws — comes from that bundle's copy of `@devmentor/core`, while `redirectHandler` in the route bundle checked `instanceof AppError` against its own copy. Fix: `AppError` instances carry `Symbol.for('devmentor.app-error')`; `isAppError` (brand + `status`/`code`/`message` shapes) and `isValidationError` (code + `fieldErrors` object) replace every `instanceof` on our errors (`apiHandler.toAppError`, the envelope's `fieldErrors`, so `redirectHandler` too). Checked the other `instanceof`s: zod 4's `ZodError` `instanceof` uses `Symbol.hasInstance` over `_zod.traits` (identity-independent); `UniqueConstraintViolationException` comes from `@mikro-orm/postgresql`, which is in `serverExternalPackages` (one `require`d copy per process), so `AccountService`'s check is safe. Regression tests: `vi.resetModules()` + a second import of `./errors` → `redirectHandler` maps the foreign error to its code without logging, `apiHandler` to its status/envelope incl. `fieldErrors` (both fail before the fix); `errors.test.ts` covers the guards. The production integration suite could not catch it.
- `serverMinification: false` kept: it is the same root cause (classes from the first bundle held in a process-wide singleton) on MikroORM's side; an identity-independent alternative would be an explicit stable entity name for the metadata lookup or one shared (external) copy of `@devmentor/db`, neither clearly better now. Any new `instanceof` on our own classes across the container boundary must use a brand like `isAppError`.
- Logger: `err.code` is kept (`23505`, `ECONNRESET`, AppError codes) — `err.code` is listed in the redact paths so pino gives `err` its own redactor and the censor sees the real path `['err', 'code']` (wildcard matches report a symbol, not the key); every other `code` (top level, `query.code`, `error.code`, …) is still `[REDACTED]`. ### Phase 2 review (Qodo)
Qodo reviewed the branch without tests, `.env.example` and stories; each finding checked against the code, real ones reproduced by a test that fails without the fix.
- [Security] Concurrent resends leave old links valid — **fixed**. Real: `resendVerification` retired older links and inserted the new one in separate statements with no per-user serialization; reproduced by a new integration test (2 parallel resends → 2 live links). Now the password check, the retirement and the insert run in one `em.transactional` that first reads the user `FOR UPDATE` (`lockMode: LockMode.PESSIMISTIC_WRITE`, `refresh: true`; `LockMode` re-exported from `@devmentor/db`), so parallel resends run one after another → exactly one live link.
- [Security] Resends can restore password-reset links — **fixed**. Real: a resend that passed its `password_hash IS NULL` check before set-password committed inserted a live link afterwards, and `setPasswordFromLink` would accept it and overwrite the password; reproduced in-process (resend started the moment hashing ends, i.e. during set-password's transaction) → password set and 1 live link. Now `setPasswordFromLink` takes the same user-row lock inside its transaction, refuses an account that already has a password (400 `VERIFICATION_LINK_INVALID`, token not consumed — a link only sets the first password; reset is out of scope) and retires the user's other live links on success; with the lock a resend after the commit sees the password and sends nothing. Spec rows for verify-email/resend amended. The HTTP integration case "a fresh link re-sets the password and ends the old session" encoded the old behaviour (a link inserted by SQL for an account with a password); it now asserts the refusal with password, `session_version` and the old session unchanged.
- [Correctness] GitHub retries lose the requested page — **fixed**. Real: every failure redirected to `/sign-in?error=<code>` without `returnTo`, so "Continue with GitHub" after a cancel/outage landed on home. `redirectHandler` now gives handlers `keepReturnToOnError(returnTo)` (passed through `safeReturnTo`, refused/absent → nothing), and the error redirect adds `&returnTo=`; the start route keeps its query's safe `returnTo` (before the config checks, so `github_unavailable` keeps it); the callback keeps the `dm_oauth` `returnTo` only when the `state` matched the signed cookie, so cancel / GitHub errors / account conflicts keep it and `github_state_invalid` drops it. `/sign-in` already reads `returnTo` from the query. To read the state on a cancel, the callback now checks `SESSION_SECRET` first (a cancel without it → `github_unavailable`; the start route needs it anyway). Unit tests in `redirectHandler.test.ts` and `github-sign-in.test.ts`.
- [Setup] Fresh installs cannot complete email auth — **not real**: `.env.example` has `SESSION_SECRET=` (filled by `npm run setup`) and `APP_URL=http://localhost:3000`; Qodo skipped the file.
- [Tests] Environment defaults break core tests; New exports break the core entry tests; Production checks break a container test — **not real**: tests were excluded from the review input; `npm run validate` is green (they were updated with the code). Note: a module-level `LockMode.PESSIMISTIC_WRITE` constant did break the `container`/`index` tests (their `@devmentor/db` mock has only `getOrm`), so the lock options are built by a function at call time.
