### Phase 1 review (Qodo)
Qodo reviewed `main..HEAD`; each finding checked against the code with a test that fails without the fix.
- [Security] Concurrent links can claim one account — **fixed**. Real: rule 2 read `github_id IS NULL`, then wrote it through the unit of work (`UPDATE … WHERE id = ?`), so two callbacks for different GitHub ids with one verified email both signed in (last id stayed linked); reproduced by a new integration test (stub persona `<base>--<suffix>` shares `<base>`'s email) before the fix. Now `AccountService.linkGithub` is one `em.nativeUpdate(User, { id, githubId: null }, …)` + `em.refreshOrFail`; the loser sees the winner's id → rule 3 conflict (or rule 1 for the same GitHub account). Unit tests (fake em `nativeUpdate`/`refreshOrFail`) + integration race.
- [Correctness] Signed-in users can enter a redirect loop — **fixed (narrower than claimed)**. No infinite loop is reachable: guards and `/sign-in` share one memoized session check, and each `/sign-in?returnTo=/sign-in?…` hop strips one level. But a signed-in user was sent back to an auth page (`returnTo=/sign-in…`, `/register…`) — pointless bounces, and the GitHub callback could land on `/sign-in` too. `safeReturnTo` now rejects `/sign-in`, `/register`, `/verify-email` (falls back to home); unit tests (`return-to`, `SignInContent`) + browser test.
- [Reliability] Failed cleanup mislabels GitHub outages — **fixed**. Real: on a non-2xx response `await response.body?.cancel()` rejects when the body stream is errored (e.g. the timeout fired after the headers), and that raw error replaced the 503 → `error=unexpected` instead of `github_unavailable`, upstream status not logged. Cleanup errors are now swallowed; regression test in `outbound.test.ts`.
- [Setup] Fresh local installs cannot sign in — **not real**: `.env.example` has `SESSION_SECRET=` (line 10) and `createEnv` fills it; Qodo skipped `.env.example` as a secret file and saw the base version. Added a test that runs `createEnv` on the repository's own `.env.example` and gets a 64-hex secret.

### Phase 1 manual test
- [Bug] `mock-unverified` under `next dev` landed on `/sign-in?error=unexpected` (log: `GithubEmailUnverifiedError` … "Unhandled redirect error") instead of `github_email_unverified` — **fixed**. Root cause: the DI container is one per process (`globalThis`) and is built by whichever server bundle calls it first (here a page, `ssr/` chunk), so every service — and the `AppError` subclasses it throws — comes from that bundle's copy of `@devmentor/core`, while `redirectHandler` in the route bundle checked `instanceof AppError` against its own copy. Fix: `AppError` instances carry `Symbol.for('devmentor.app-error')`; `isAppError` (brand + `status`/`code`/`message` shapes) and `isValidationError` (code + `fieldErrors` object) replace every `instanceof` on our errors (`apiHandler.toAppError`, the envelope's `fieldErrors`, so `redirectHandler` too). Checked the other `instanceof`s: zod 4's `ZodError` `instanceof` uses `Symbol.hasInstance` over `_zod.traits` (identity-independent); `UniqueConstraintViolationException` comes from `@mikro-orm/postgresql`, which is in `serverExternalPackages` (one `require`d copy per process), so `AccountService`'s check is safe. Regression tests: `vi.resetModules()` + a second import of `./errors` → `redirectHandler` maps the foreign error to its code without logging, `apiHandler` to its status/envelope incl. `fieldErrors` (both fail before the fix); `errors.test.ts` covers the guards. The production integration suite could not catch it.
- `serverMinification: false` kept: it is the same root cause (classes from the first bundle held in a process-wide singleton) on MikroORM's side; an identity-independent alternative would be an explicit stable entity name for the metadata lookup or one shared (external) copy of `@devmentor/db`, neither clearly better now. Any new `instanceof` on our own classes across the container boundary must use a brand like `isAppError`.
- Logger: `err.code` is kept (`23505`, `ECONNRESET`, AppError codes) — `err.code` is listed in the redact paths so pino gives `err` its own redactor and the censor sees the real path `['err', 'code']` (wildcard matches report a symbol, not the key); every other `code` (top level, `query.code`, `error.code`, …) is still `[REDACTED]`. Test in `logger.test.ts`.
